# 서버에서 방 ID 발급

## 목적과 범위

클라이언트의 `mock-${Date.now()}` 식별자 생성을 Vercel Functions의 UUID 발급으로 교체한다. 서버에서 방 ID를 발급하고, 브라우저는 응답받은 ID로 기존 방 URL과 QR을 표시한다.

이번 단계는 ID 발급만 구현한다. 방 정보의 DB 저장·조회, 존재 여부 검증, 입장·세션·만료·실시간 동기화는 후속 작업이다. 인원수는 검증하고 응답에 포함하지만 저장하지 않는다. 기존 `mock-*` URL도 QR 화면을 계속 표시한다.

## API

- `POST /api/rooms`
- 요청 JSON: `{ "playerCount": 4 }`. 정수 4·5·6만 허용한다.
- 서버의 `crypto.randomUUID()`로 ID를 발급한다.
- 성공: `201`, `{ "id": "<UUID>", "playerCount": 4 }`.
- 잘못된 JSON 또는 인원수: `400`, `{ "error": "안내 메시지" }`.
- POST 이외의 메서드: `405`, `Allow: POST`, `{ "error": "안내 메시지" }`.
- 함수 메모리나 파일에 방 상태를 보관하지 않는다.

## 사용자 흐름

1. 방 만들기 버튼을 누르면 클릭 시점의 인원수를 상대 경로 `/api/rooms`로 전송한다.
2. 요청 중에는 생성 버튼과 인원 선택을 비활성화하고 `생성 중…`을 표시한다.
3. 성공 응답의 ID로 `/rooms/:roomId`에 이동한다.
4. 브라우저에서 현재 출처와 경로로 URL을 조립하고 QR을 렌더링한다.
5. 통신 오류나 실패 응답이면 시작 화면에 오류를 표시하고 다시 요청할 수 있게 한다. 클라이언트에서 대체 ID를 만들거나 자동 재시도하지 않는다.

## 구현과 개발 환경

- 루트 `api/rooms.ts`에 표준 Request·Response 기반 fetch 핸들러를 둔다. 배포 시 Vercel Node.js 런타임에서 실행한다.
- 로컬은 기존 ADR에 따라 별도 Bun.serve API 서버와 Vite 프록시를 사용한다. 동일한 함수 핸들러를 호출하며 로컬 서버는 `api/` 밖에 둔다.
- `bun run dev`는 Vite를, `bun run dev:api`는 `127.0.0.1:3001`의 API 서버를 실행한다. 두 터미널에서 각각 실행한다.
- Vite `/api` 프록시는 로컬 API 서버로 연결하고, 기존 방 URL의 SPA rewrite를 유지한다.
- 서버·로컬 실행 코드·테스트를 TypeScript 검사에 포함한다. 테스트는 Bun 테스트 러너를 사용한다.

## 수용 기준과 검증

- 4·5·6명 요청은 UUID와 요청 인원수로 응답하며, 요청마다 다른 ID를 발급한다.
- 잘못된 JSON 및 누락·문자열·소수·범위 밖 인원수는 거부한다. POST 이외 메서드도 거부한다.
- Vite 프록시를 통한 API 호출, 서버 ID로 화면 이동, 해당 URL의 QR 표시를 확인한다.
- 요청 중 중복 클릭 방지, 실패 표시와 재시도, 기존 URL의 직접 접속·새로고침을 확인한다.
- `bun test`, `bun run build`, `bun run lint`가 통과해야 한다.
- Vercel Preview에서 API 응답과 방 URL 새로고침을 별도로 검증한다. 로컬 서버 검증은 배포 검증을 대체하지 않는다.
