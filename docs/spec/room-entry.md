# 방 입장

## 목적과 사용자 문제

방을 만든 호스트는 QR 아래 버튼으로, 초대받은 사람은 QR 스캔으로 같은 방의 참가 화면에 접근한다. 현재 QR은 QR 표시 화면 자체를 가리키므로, 입장하려는 사람이 다시 QR 화면을 보게 되는 문제를 해결한다.

## 범위

- QR 표시 화면과 참가 화면의 URL 및 역할을 분리한다.
- QR 아래에 `입장` 버튼을 추가하고 새 탭으로 참가 화면을 연다.
- QR과 버튼이 동일한 참가 URL을 사용한다.
- 참가 화면은 [방 만들기 스펙](room-creation.md)의 입장 정보 입력 흐름으로 연결한다. 입력 항목과 이후 좌석 선택 요구사항은 해당 스펙을 따른다.

## 화면과 URL

| 화면 | URL | 역할 |
| --- | --- | --- |
| QR 표시 화면 | `/rooms/:roomId` | 방 생성 후 QR과 그 아래 `입장` 버튼 표시 |
| 참가 화면 | `/rooms/:roomId/join` | 해당 방의 입장 정보 입력 |

예를 들어 `/rooms/1792684449634`의 QR과 버튼은 모두 `https://reverse-destiny.vercel.app/rooms/1792684449634/join`을 사용한다. 배포 주소를 고정하지 않고 현재 서비스의 origin과 해당 방 ID로 참가 URL을 구성한다.

## 사용자 흐름

1. 호스트가 방을 만들면 `/rooms/:roomId`에서 QR과 `입장` 버튼을 확인한다.
2. 호스트가 `입장` 버튼을 클릭하면 `/rooms/:roomId/join`이 새 탭으로 열린다. 원래 탭에는 QR 표시 화면이 유지된다.
3. 초대받은 사람은 QR을 스캔해 호스트의 새 탭과 동일한 참가 URL을 연다.
4. 두 경로 모두 QR 표시 화면 대신 해당 방의 입장 정보 입력 화면을 표시한다.
5. 입장 정보 입력 이후에는 기존 좌석 선택·확정 흐름을 따른다.

## 요구사항과 결정 이유

- `입장` 버튼은 QR 바로 아래에 표시한다.
- 버튼에는 새 탭으로 열린다는 안내를 제공한다.
- 버튼 클릭은 사용자 동작에 따라 새 탭을 열어야 하며, 원래 탭을 참가 화면으로 이동시키지 않는다.
- QR에 담는 절대 URL과 버튼이 여는 절대 URL은 동일해야 한다. 방 ID와 경로뿐 아니라 쿼리와 해시를 포함한 전체 주소를 일치시킨다.
- 참가 화면은 QR 표시 화면과 구분되며, 입장 정보 입력을 표시한다. QR 화면으로 다시 연결하지 않는다.
- 참가 URL을 직접 열거나 새로고침해도 해당 방의 참가 화면으로 접근할 수 있어야 한다. 원래 탭의 메모리나 라우터 전달 상태에 의존하지 않는다.
- QR을 표시하거나 버튼으로 참가 화면을 열 때 새 방을 생성하지 않는다. 두 접근 경로 모두 생성된 방 ID를 유지한다.
- 버튼과 QR은 접근 수단만 다르며, 접근 수단 자체로 호스트 권한을 부여하지 않는다.
- UX 결정의 배경과 대안은 [방 입장 UX ADR](../ADR/2026-10-23-006-room-entry-ux.md)을 따른다.

## 수용 기준

- `/rooms/:roomId`에서 QR 아래에 `입장` 버튼과 새 탭 안내가 보인다.
- 버튼을 클릭하면 새 탭의 주소가 같은 방의 `/rooms/:roomId/join`이며, 원래 탭은 QR 화면에 남는다.
- QR을 디코딩한 URL과 버튼의 목적지 URL이 완전히 같다.
- QR 스캔과 버튼 클릭 모두 동일한 방의 입장 정보 입력 화면을 표시하며, QR 표시 화면을 다시 보여주지 않는다.
- 참가 URL을 별도 브라우저에서 직접 열거나 새로고침해도 참가 화면이 표시된다.
- 다른 방의 QR과 버튼은 각각 해당 방 ID의 참가 URL을 사용한다.
- QR 표시와 참가 화면 접근만으로 추가 방 생성 요청이 발생하지 않는다.

## 미결정 사항

- 참가 화면에서 사용할 방 조회 API와 응답 형식
- 존재하지 않거나 종료된 방의 참가 화면 안내와 복귀 동작
