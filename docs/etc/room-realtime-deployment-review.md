# 방 입장, 실시간 통신 및 배포 구조 검토

- 작성일: 2026-09-06
- 상태: 검토 중. ADR로 확정한 기술 결정이 아니다.

## 서비스 방향

회원가입이나 로그인 화면 없이, 같은 장소의 4~6명이 QR을 통해 방에 입장하여 게임을 진행한다. 사용자가 버튼을 눌렀을 때 방을 생성하는 흐름은 이 사용 방식에 적합하다.

다만 로그인 절차를 생략하더라도 서버는 플레이어를 구분하고 행동 권한을 확인해야 한다. 자신의 좌석만 변경할 수 있어야 하며, 다른 플레이어의 비공개 명식을 조회할 수 없어야 한다.

## 제안하는 방 생성 및 입장 흐름

1. 사용자가 `방 만들기` 버튼을 누르면 서버에 방 생성을 요청한다.
2. 서버는 방을 생성하고 입장 URL을 반환한다.
3. React 화면에서 입장 URL을 QR로 렌더링한다.
4. 각 플레이어는 자신의 휴대폰으로 QR을 스캔하여 입장한다.
5. 서버는 각 플레이어에게 익명 세션을 발급한다.
6. 플레이어는 출생 정보와 성별을 입력하고 좌석을 선택·확정한다.
7. 입장 이후 게임 상태를 실시간으로 공유한다.

QR 이미지 자체는 서버에서 생성하지 않아도 된다. 서버가 반환한 입장 URL을 브라우저에서 QR로 그리는 것으로 충분하다. QR에는 출생 정보나 개인 명식을 넣지 않는다.

구체적인 제품 요구사항은 [방 만들기 스펙](../spec/room-creation.md)을 참고한다.

## 로그인 없는 익명 세션

- 별도의 가입 절차 없이 임시 세션을 발급하여 플레이어를 구분한다.
- 방 입장 URL은 공유하지만, 플레이어별 세션은 각자의 휴대폰에 따로 유지한다.
- 새로고침이나 일시적인 연결 끊김 이후에도 같은 플레이어로 복귀할 수 있어야 한다.
- 서버에서 세션을 확인하여 본인의 좌석 변경 등 허용된 행동만 처리한다.

이는 계정 기반 로그인 없이 사용하는 구조이며, 서버의 식별·권한 확인까지 없애는 구조는 아니다.

## 실시간 통신 비교

| 기준 | HTTP 요청 + SSE | WebSocket |
| --- | --- | --- |
| 좌석·질문 선택 전송 | HTTP 요청 | 연결된 소켓 |
| 서버의 변경 알림 | SSE로 수신 | 같은 소켓으로 수신 |
| 현재 게임 요구사항 충족 | 가능 | 가능 |
| 연결 복구 | EventSource의 자동 재연결 지원, 상태 복원은 별도 구현 | 재연결과 상태 복원 구현 필요 |

SSE는 서버에서 브라우저로 보내는 단방향 통신이다. 사용자 행동을 HTTP 요청으로 보내고 변경 알림을 SSE로 받으면 버튼 중심의 턴제 게임을 구현할 수 있다. [MDN SSE 문서](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

현재 추천은 WebSocket이다. 성능상 필수라서가 아니라, 방에 연결된 플레이어의 행동과 상태 변경을 하나의 통신 경로에서 다루기 편하기 때문이다. 방 생성과 최초 입장은 HTTP로 처리하고, 입장 이후 게임 진행은 WebSocket으로 처리하는 구성을 제안한다.

## 통신 방식과 무관하게 필요한 상태 관리

- 서버가 방의 최종 상태를 결정한다. 두 사람이 같은 빈 좌석을 선택하면 한 명만 승인한다.
- 휴대폰이 다시 연결되면 현재 방 상태를 받아 화면을 복원한다.
- 비공개 명식은 다른 플레이어에게 전송하지 않는다. 화면에서 숨기는 것만으로 처리하지 않는다.
- 좌석, 오야의 밝혀진 명식, 현재 선택한 질문 등 공개 가능한 게임 상태만 공유한다.
- 서버 재시작이나 유휴 상태 전환 이후에도 게임을 복원할 수 있도록 방 상태의 저장 방식을 정해야 한다.

## 배포 플랫폼 비교

| 후보 | 적합한 이유 | 고려할 점 |
| --- | --- | --- |
| Cloudflare Workers + Durable Objects | 방별 상태와 실시간 연결을 관리하는 구조에 적합 | Cloudflare 실행·저장 방식 학습 필요 |
| Render Web Service | 일반적인 서버에서 WebSocket을 직접 구현하기 편함 | 서버 재시작 시 복구와 여러 인스턴스 간 방 관리 설계 필요 |

### Cloudflare Workers + Durable Objects

현재 요구사항 기준의 우선 추천이다.

- React + Vite 정적 파일과 API를 함께 배포할 수 있다. [공식 배포 가이드](https://developers.cloudflare.com/workers/framework-guides/web-apps/react/)
- Durable Objects는 상태 저장과 실시간 조정을 지원한다. 이를 활용하여 방 하나를 Durable Object 하나에 대응시키는 설계를 제안한다. [공식 개요](https://developers.cloudflare.com/durable-objects/)
- WebSocket Hibernation은 연결을 유지하면서 유휴 상태의 실행 비용을 줄일 수 있다. 질문을 읽거나 대화하는 동안 입력이 없는 게임 특성과 맞는다. [공식 WebSocket 문서](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- Bun은 의존성 설치와 개발 도구로 유지하며, 배포된 서버 코드는 Workers 런타임에서 실행한다.

### Render Web Service

일반 서버 방식으로 구현하거나 Bun을 서버 런타임으로도 사용하려는 경우 검토할 대안이다. Render는 WebSocket 연결을 지원한다. [공식 WebSocket 문서](https://render.com/docs/websocket)

서버 메모리에만 방 상태를 두면 재시작 시 유실될 수 있으므로 복구 방식을 정해야 한다. 여러 서버 인스턴스로 확장할 경우 같은 방의 연결과 상태를 어떻게 관리할지도 별도 설계가 필요하다.

## 현재 추천 구성과 후속 결정

추천 구성은 다음과 같으며, 아직 채택된 결정은 아니다.

- 로그인 없는 익명 세션
- HTTP 요청을 통한 방 생성
- 브라우저에서 입장 URL을 QR로 렌더링
- WebSocket을 통한 게임 상태 동기화
- Cloudflare Workers + Durable Objects 배포

실시간 통신과 배포 플랫폼을 확정하면 ADR로 기록한다. 세션 유지·재입장 방식과 방 상태의 저장·만료 정책은 제품 요구사항과 함께 구체화한다.
