# Git 컨벤션

이 저장소의 브랜치, 커밋, Pull Request(PR), 병합 규칙을 정의합니다.

## 브랜치

- `main`: 배포 가능한 상태를 유지하는 기본 브랜치입니다.
- 작업은 최신 `main`에서 분기하고, PR을 통해 `main`에 병합합니다.
- 하나의 브랜치에서는 하나의 목적에 집중합니다. 별도의 `develop` 브랜치는 사용하지 않습니다.
- 브랜치 이름은 `<type>/<short-description>` 형식으로 작성합니다. 설명은 소문자 영문 kebab-case를 사용합니다.
- 이슈가 있으면 `<type>/<issue-number>-<short-description>` 형식으로 번호를 붙일 수 있습니다.

```text
feat/room-creation
fix/duplicate-room-entry
docs/game-rules
chore/update-dependencies
feat/12-room-creation
```

## 커밋 메시지

기존 이력과 같이 타입은 영문 소문자, 설명은 한국어를 기본으로 작성합니다. 코드 식별자와 기술 용어는 영문을 사용할 수 있습니다.

```text
<type>: <설명>

[선택: 변경 이유와 주요 내용]

[선택: 관련 이슈]
```

| 타입 | 용도 |
| --- | --- |
| `feat` | 사용자 기능 추가 또는 변경 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 또는 수정 |
| `style` | 동작에 영향을 주지 않는 포맷, 공백 등의 변경 |
| `refactor` | 동작을 유지하는 코드 구조 개선 |
| `perf` | 성능 개선 |
| `test` | 테스트 추가 또는 수정 |
| `build` | 빌드 도구 및 빌드 설정 변경 |
| `ci` | CI 워크플로 변경 |
| `chore` | 의존성 관리 등 그 외 유지보수 |
| `revert` | 기존 커밋 되돌리기 |

- 제목은 무엇이 바뀌었는지 알 수 있도록 간결하게 작성하고 끝에 마침표를 붙이지 않습니다.
- UI의 색상, 배치 등 사용자에게 보이는 변경은 목적에 따라 `feat` 또는 `fix`를 사용합니다. `style`은 코드 표기에만 사용합니다.
- 본문이 필요하면 제목 다음에 빈 줄을 두고, 변경 이유와 필요한 맥락을 적습니다.
- 하나의 커밋은 하나의 논리적 변경을 담습니다. 관련 없는 수정과 전체 파일 포맷 변경을 섞지 않습니다.
- 기능에 필요한 코드와 관련 문서·테스트는 같은 커밋에 포함할 수 있습니다.

```text
feat: 방 생성 화면 추가
fix: 같은 방에 중복 입장하는 문제 수정
docs: 게임 승리 조건 명확화
refactor: 시작 화면의 버튼 컴포넌트 분리
chore: react-router 의존성 업데이트
```

## Pull Request

- 대상 브랜치는 `main`으로 지정합니다.
- PR 제목은 커밋 메시지와 같은 `<type>: <설명>` 형식을 사용합니다.
- 하나의 PR은 하나의 목적을 다룹니다. 검토하기 어려울 만큼 커지면 독립적으로 병합 가능한 단위로 나눕니다.
- 본문에는 변경 내용과 이유, 확인 방법과 결과를 기록합니다.
- 화면이 바뀌면 스크린샷이나 영상을 첨부합니다.
- 관련 이슈가 있으면 연결합니다. 병합으로 해결되는 이슈만 `Closes #12`처럼 자동 종료 키워드를 사용합니다.

다음 양식을 PR 본문에 복사해 사용합니다.

```markdown
## 변경 내용

- 무엇을 왜 변경했는지

## 확인 방법 및 결과

- 실행한 검사와 결과
- 직접 확인한 사용자 흐름과 결과
- 실행하지 못한 검사가 있다면 그 이유

## 관련 이슈

- 해당하는 경우 작성

## 화면 변경

- 해당하는 경우 스크린샷 또는 영상 첨부
```

## 검증과 병합

- 코드가 바뀌면 PR 병합 전에 다음 명령이 통과하는지 확인합니다.

  ```bash
  bun run lint
  bun run build
  ```

- 변경한 기능의 사용자 흐름을 직접 확인하고 PR에 결과를 적습니다. 버그 수정은 기존 문제가 재현되지 않는지도 확인합니다.
- 문서만 변경했다면 내용, 링크, Markdown 표시를 확인하고 코드 검사는 생략할 수 있습니다.
- 리뷰 의견과 충돌을 해결한 뒤 병합합니다. 다른 협업자가 있으면 최소 1명의 승인을 받고, 혼자 작업할 때는 diff를 직접 검토합니다.
- 기본 병합 방식은 **Squash and merge**입니다. 최종 커밋 제목과 본문을 PR 전체 변경을 설명하도록 정리합니다.
- 병합한 원격 작업 브랜치는 삭제합니다. 로컬 브랜치는 필요한 작업이 남아 있지 않은지 확인한 후 정리합니다.

## 작업 시 주의사항

- 커밋 전에 `git status`와 `git diff --staged`로 포함할 파일과 변경 내용을 확인합니다.
- `.env`, API 키, 토큰 등 비밀 정보와 `node_modules/`, `dist/` 같은 설치·빌드 결과물은 커밋하지 않습니다. 의존성을 바꾸면 관련 lockfile도 함께 커밋합니다.
- `main`과 여러 사람이 사용하는 브랜치에는 force push를 하지 않습니다.
- 개인 작업 브랜치의 이력을 수정해 다시 올려야 한다면 `git push --force-with-lease`를 사용합니다. 다른 사람의 작업이 포함돼 있다면 먼저 조율합니다.
- 이미 `main`에 병합한 변경을 취소할 때는 이력을 삭제하지 않고, `git revert <commit>`으로 되돌리는 커밋을 만들어 PR로 병합합니다.

이 문서는 작업 규칙을 정의합니다. 브랜치 보호, 필수 리뷰, 병합 방식 등의 GitHub 저장소 설정은 별도로 적용해야 합니다.
