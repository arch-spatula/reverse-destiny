# Software Factory

이 스킬을 실행하는 에이전트는 오케스트레이터다. [설계 ADR](../../../docs/ADR/2026-10-23-005-spec-driven-software-factory.md)을 읽고, 요청된 스펙과 작업 범위에 한해 아래 흐름을 실행한다. ADR의 상태를 임의로 변경하지 않는다.

## 역할과 실행 준비

- A(구현): 작업 분해, 제품 코드 구현, 피드백 판단·반영, 자체 검증.
- B(QA): 스펙에서 테스트 도출, 테스트 코드 작성·수정, C 승인 후 QA 실행, 실패 원인 분석.
- C(검토): 테스트 코드의 타당성 검토와 승인, QA 실행 근거 검토. 제품 코드나 테스트 코드를 대신 수정하지 않는다.
- 오케스트레이터: 세 에이전트를 호출하고 모든 작업 배정, 버전 전달, 피드백 전달, 의견 중재와 완료 판정을 담당한다.

멀티 에이전트 도구가 사용 가능한지 확인한다. 사용할 수 없다면 단일 에이전트로 역할을 흉내 내고 완료했다고 보고하지 말고, 제약을 알린다. 역할마다 별도 에이전트를 사용하고 가능한 한 같은 에이전트에 후속 작업을 전달한다. A가 개발하는 동안 B와 C를 대기시키지 않도록 세 작업 에이전트를 함께 운용한다.

대상 스펙 버전, 수용 기준, 작업 범위, 기존 변경사항을 확인한다. 스펙 해석에 따라 구현이 달라지는 모호함은 사용자에게 확인하고, 그 답에 의존하지 않는 작업은 계속한다. 테스트 도구와 실행 명령은 저장소에서 확인하며, 새로운 테스트 도구가 필요하면 해당 작업에 필요한 최소 구성만 추가한다.

## 작업 분해와 범위 유지

A를 호출할 때 스펙과 함께 다음 지침을 전달한다.

> 작업을 검증 가능한 작은 단위로 촘촘하게 분해하라. 각 항목에 ID, 목적, 대응하는 수용 기준, 변경 대상, 완료 조건을 명시하고 먼저 제출하라. 변경은 작업 항목에 연결하라. 요청받지 않은 기능 추가나 관련 없는 리팩터링을 수행하지 마라. 목록 밖의 작업이 필요하면 이유와 영향을 보고하라. QA를 기다리지 말고 범위 내 다음 개발 작업을 계속하라.

오케스트레이터가 분해 목록과 요청 범위의 대응을 확인한 뒤 A에게 구현을 진행시킨다. B와 C에도 원본 스펙과 작업 목록, 공유 인터페이스와 의존성 주입 경계를 전달한다. 검증 기준은 A의 구현 설명만으로 정하지 않는다. 요구사항 확장은 사용자에게 확인하며, 기존 요청 범위 내 보완에 매번 사용자 승인을 요구하지 않는다.

## 개발과 독립된 QA 흐름

1. A는 작은 작업 단위의 변경이 준비되면 오케스트레이터에 알리고 다음 개발을 계속한다. **B의 테스트 작성, C의 검토, B의 QA 실행 때문에 A를 멈추지 않는다.**
2. 오케스트레이터는 변경사항마다 QA Task를 만들어 B에게 비동기로 배정한다. Task에는 ID, 작업 항목과 수용 기준, 변경 범위, 재현 가능한 대상 코드 버전, 실행 환경·명령을 담는다.
3. B는 해당 버전에 대한 테스트 코드를 작성해 전달한다. 오케스트레이터는 테스트 버전과 대상 코드를 C에게 보내 검토를 요청한다.
4. C는 `APPROVED` 또는 `CHANGES_REQUESTED`와 근거를 반환한다. 테스트 보완은 B가 수행하고 다시 C의 검토를 받는다. 승인 전 결과 확인을 위한 시험 실행은 가능하지만, 공식 QA 판정은 승인 후 수행한다.
5. C의 구현 관련 피드백은 오케스트레이터가 A에게 비동기로 전달한다. A는 타당한 피드백을 작업 목록에 연결해 반영하고, 이견이 있으면 근거를 보고한다. 오케스트레이터는 스펙과 재현 근거로 중재하며 미해결 쟁점을 임의로 폐기하지 않는다.
6. B는 C가 승인한 테스트를 지정된 코드 버전에서 실행하고, 수용 기준별 결과, 실행 명령, 실패 근거와 미검증 항목을 보고한다. C는 결과의 근거가 판정을 뒷받침하는지도 확인한다.

Task별 상태는 `작성 중 → 검토 중 → APPROVED → 실행 중 → 통과/실패`로 관리한다. 수정된 테스트는 검토 중으로 되돌린다. 진행 상황과 근거는 Task별로 정리해 후속 에이전트가 이어받을 수 있게 한다. 별도 영구 저장 시스템을 만들지는 않는다.

### 버전과 쓰기 범위

A는 제품 코드, B는 테스트 코드를 수정한다. 동일 파일을 동시에 수정하지 않도록 작업을 배정한다. 공유 테스트 설정 변경은 오케스트레이터가 소유자를 정한다.

QA는 실행 중 변경되지 않는 별도 작업 공간의 스냅샷에서 수행한다. 커밋 ID 또는 기준 커밋과 변경 패치 등으로 미커밋 변경까지 재현할 수 있게 전달한다. 작업 공간 분리는 기존 도구나 임시 복사본으로 해결하고 사용자 변경사항을 덮어쓰지 않는다. A가 수정 중인 작업 디렉터리에서 QA를 실행해 고정 버전 검증이라고 보고하지 않는다. 테스트 변경을 통합할 때는 승인된 버전을 사용하고 이후 제품 변경의 영향을 다시 확인한다.

## C의 테스트 검토 기준

- 수용 기준과 테스트가 대응하며, 잘못된 제품 동작에서 실제로 실패하는가? 단언문 부재, 항상 참인 조건, 모의 객체 반환값만 재확인하는 테스트를 거부한다.
- 스펙에 명시된 실패·경계 조건을 다루는가? 구현 로직을 복제해 같은 오류를 공유하지 않는가?
- 외부 API 호출이 의존성 주입으로 대체 가능한가? 자동 테스트가 실제 외부 API의 가용성·지연·호출 제한에 의존하지 않는가? 실제 API 연동 검증은 별도로 구분한다.
- 시간, 난수, 공유 상태, 실행 순서, 비동기 처리 때문에 flaky해질 수 있는가? 고정 대기나 무조건 재시도로 문제를 숨기지 않는가?
- 실행한 코드와 테스트 버전, 실행 결과가 명시되어 있고 그 근거가 통과 판정을 뒷받침하는가?

## 실패 분류와 반복

오케스트레이터는 B의 분석과 C의 검토를 받아 스펙, 기대값, 실행 결과를 비교한다.

- 테스트 결함: B가 기대값·검증 방법·비결정성 문제를 수정한다. C가 다시 승인한 뒤 QA를 재실행한다.
- 구현 결함: A가 타당성을 확인해 수정하고 자체 검증한다. 변경은 새로운 QA Task로 보내고 관련 테스트의 타당성을 다시 확인한다.
- 양쪽 결함: A와 B에 각각 보완을 배정한다.
- 원인 불명: 재현과 원인 분석부터 수행한다. 실행 환경 문제나 실행 불가를 통과로 간주하지 않는다.

현재 구현을 통과시키기 위한 기대값 변경, 테스트 삭제·비활성화로 결함을 숨기지 않는다. A는 피드백 처리 중에도 진행 가능한 다른 개발 작업을 계속한다.

동일 원인이 수정 후에도 반복되고 새 근거나 개선이 없으면 무제한 재시도하지 않는다. 재현 근거, 시도한 수정, 남은 쟁점을 사용자에게 보고하고 의존하지 않는 작업만 계속한다. 명시된 시간·비용·재시도 한도가 있으면 우선 적용한다. 해결하지 못한 작업을 완료로 표시하지 않는다.

## 최종 완료 판정

A는 전체 구현을 마치면 B와 C를 기다리지 않고 자체 검증한다. 오케스트레이터는 통합된 최종 코드와 테스트 버전에 대해 B의 QA와 C의 검토를 배정한다. 이전 버전의 QA 통과로 최신 버전을 통과 처리하지 않는다.

다음을 모두 확인한 뒤 완료를 보고한다.

- 모든 수용 기준에 검증 결과와 근거가 있고, A의 자체 검증과 B의 QA가 통과했다.
- C가 최종 테스트와 실행 근거를 타당하다고 판단했다.
- 미해결 결함·피드백·미검증 항목이 없고 검증 이후 변경이 없다.
- 최종 diff가 작업 목록 및 요청 범위에 대응하고 요청하지 않은 변경이 없다.

최종 보고에는 변경 내용, 수용 기준별 결과, 대상 버전, 실행한 검사와 남은 제약을 담는다. 이 스킬 실행은 커밋·푸시·병합·배포 권한을 추가하지 않는다. 해당 작업은 사용자의 요청과 기존 권한 범위에 따른다.
